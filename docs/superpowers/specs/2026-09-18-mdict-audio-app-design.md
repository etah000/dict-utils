# MDict 生词音频应用设计

日期：2026-09-18  
状态：待审核

## 1. 背景与目标

本项目在现有 `readmdict.py` 解析能力上构建一个仅支持 Windows 的单用户离线桌面应用。应用需要导入多个 MDX/MDD 词典，按用户配置的词典优先级查询生词，为每个生词选择发音和限定数量的带音频例句，最终合成为一个音频文件。

目标规模为约 100 万词条、20 万以上音频资源、总资源低于 10 GB。首版不使用 TTS；缺失音频时跳过并在结果中报告。已有的文本转语音应用作为后续集成项，不纳入首版。

## 2. 技术决策

- 开发语言：Python 3。
- 桌面界面：PySide6 + Qt Widgets，不使用 QML。
- 结构化存储：SQLite `dictionary.db`。
- 音频存储：多个 SQLite BLOB 分片库 `audio-NNN.db`，每片目标上限 2 GB。
- 音频处理：随应用分发的 FFmpeg/FFprobe。
- 打包：首版使用 `pyside6-deploy`/Nuitka 的 `standalone` 模式；稳定后再评估单文件模式。

不采用 RocksDB，因为本项目包含词典优先级、词条—例句—音频关系、事务、迁移和检索等关系型需求。音频不保存为大量独立小文件，以避免 NTFS 目录、杀毒扫描和备份开销。

## 3. 总体架构

```text
PySide6 UI
   │
应用服务：导入 / 查询 / 音频计划 / 音频渲染
   │
领域层：词典、词条、例句、音频引用、生成任务
   │
SQLite 目录库 ───── SQLite 音频分片库
   │                       │
MDX/MDD 解析器             FFmpeg/FFprobe
```

UI 只负责收集输入、展示状态和发送命令。MDict 解析、数据库访问和 FFmpeg 调用均位于独立服务中，不依赖 Qt，便于测试和未来与 TTS 应用合并。

建议的新代码采用包结构：

```text
src/mdict_audio_app/
├── domain/                 # 领域模型和枚举
├── importers/              # MDX/MDD 导入流程
├── parsers/                # 通用及词典专用 HTML 适配器
├── storage/                # 迁移、目录库、BLOB 分片库
├── services/               # 查询、音频计划、渲染服务
├── ui/                     # PySide6 窗口、模型和后台任务
└── main.py
```

## 4. 数据模型

`dictionary.db` 使用外键、WAL 和版本化迁移。核心表如下：

### `dictionary`

- `id`、`name`、`priority`、`enabled`
- `source_mdx_name`、`source_mdd_name`：用于诊断和重导入提示，不依赖原文件继续存在
- `mdx_sha256`、`mdd_sha256`：识别重复导入和源文件变化
- `metadata_json`：保留 MDict 头部元数据
- `adapter_name`：使用的词典解析适配器
- `status`：`IMPORTING`、`READY`、`FAILED`
- `imported_at`

### `entry`

- `id`、`dictionary_id`
- `headword`、`normalized_headword`
- `definition_html`、`definition_text`
- `source_order`

在 `(normalized_headword, dictionary_id)` 上建立索引。可选的 FTS5 表用于界面全文搜索；生成音频所需的精确查词不依赖 FTS。

### `example`

- `id`、`entry_id`
- `text`、`source_order`

### `audio_resource`

- `id`、`sha256`（唯一）、`media_type`
- `duration_ms`、`byte_size`
- `shard_id`、`blob_id`

### `audio_link`

- `id`、`entry_id`、可空的 `example_id`
- 可空的 `resource_id`；MDD 缺失或无法识别时保持为空
- `kind`：`HEADWORD` 或 `EXAMPLE`
- `resolution_status`：`MATCHED`、`MISSING` 或 `UNKNOWN`
- `source_ref`、`source_order`

### `audio_shard`

- `id`、`filename`、`byte_size`、`status`

每个 `audio-NNN.db` 仅包含：

```sql
CREATE TABLE audio_blob (
    id INTEGER PRIMARY KEY,
    sha256 BLOB NOT NULL UNIQUE,
    data BLOB NOT NULL
);
```

## 5. 词典导入流程

1. 用户选择一个或多个 MDX 文件；系统自动匹配同名 MDD，也允许手动指定。
2. 计算源文件哈希，阻止无意的重复导入；用户可选择替换已有版本。
3. 创建 `IMPORTING` 状态的词典记录，在后台线程中顺序解析 MDX。
4. 按批次写入词条，通用解析器从 HTML 中提取 `sound://` 引用；词典专用适配器进一步识别释义、例句文本、单词发音和例句发音。
5. 收集实际被引用的 MDD 路径，再顺序扫描 MDD。只导入被引用且属于支持格式的音频，避免保存无关图片、CSS 等资源。
6. 对音频计算 SHA-256；若 `audio_resource` 已存在则复用，否则写入当前 BLOB 分片。分片接近 2 GB 时创建下一片。
7. 使用 FFprobe读取格式与时长，建立 `audio_link`。
8. 完成校验后将词典状态改为 `READY`；失败时保留错误摘要并隐藏未完成词典。

不同 SQLite 文件无法共享原子事务，因此写入顺序固定为“先提交 BLOB，再提交目录引用”。崩溃最多留下无引用 BLOB，不会产生指向不存在数据的目录记录。维护操作可以按 SHA-256 清理孤立 BLOB。导入批次默认 1,000 条，并允许安全取消。

## 6. HTML 解析策略

MDict 不规定词条 HTML 的语义结构，不能只凭通用规则可靠区分单词发音和例句发音。因此采用两级解析：

- 通用解析器：提取词头、原始 HTML、纯文本和 `sound://` 引用，作为所有词典的后备能力。
- 专用适配器：使用 CSS 选择器或结构规则识别某一词典的释义、例句及音频类型。

适配器通过注册表按词典标题、文件哈希或用户选择启用。无法识别的引用标记为 `UNKNOWN`，不自动当作例句音频；界面显示解析统计，避免静默产生错误结果。

## 7. 生词选择规则

用户通过文本文件、CSV、粘贴或界面输入生词。系统统一大小写和空白，但保留原始顺序；重复词默认去重并保留第一次出现位置。

对于每个生词：

1. 在启用的词典中按 `priority ASC` 查找，选择第一个存在该词条的词典。
2. 同一词典内若存在同形词条，则按源顺序合并为一个候选；释义和例句不跨词典混合。
3. 单词发音优先取该词典；若缺失，可配置为向低优先级词典回退。
4. 只选择带有效音频的例句，按原始顺序取最多 `N` 条。
5. 加入片段前检查全局最大时长；超出时停止追加后续例句或单词。

默认值为每词 2 条例句、词间静音 800 ms、片段间静音 300 ms、全局时长不限。所有参数均可在生成页面调整。

## 8. 音频生成流程

“音频计划服务”先产生不可变的片段清单，包含生词、片段类型、来源词典、资源 ID、时长和跳过原因。该计划可在 UI 中预览，再交给渲染服务：

1. 从 BLOB 分片读取所选音频到任务临时目录。
2. 使用 FFmpeg 统一采样率、声道和编码参数。
3. 插入配置的静音并按清单顺序拼接。
4. 原子地写入目标文件，默认输出 MP3，也支持 M4A 和 WAV。
5. 同时输出 JSON 清单，记录已使用及跳过的词条、例句和资源来源。
6. 无论成功、失败或取消，清理任务临时目录。

首版缺失音频直接跳过；接口保留 `AudioProvider` 抽象，后续可增加 TTS Provider，而不改变选择与渲染流程。

## 9. 桌面界面

应用包含三个主要页面：

- 词典管理：导入、删除、启用/禁用、拖动优先级、查看条目及音频统计。
- 生词列表：导入或粘贴生词，预览命中词典、释义、例句和缺失项。
- 音频生成：设置例句数量、回退策略、静音、最大时长、格式和输出路径，并显示进度及日志。

长时间操作通过 `QThreadPool`/工作对象执行。每个工作线程创建自己的 SQLite 连接；写操作由单个导入队列串行化。UI 线程不执行数据库批量操作、MDict 解压或 FFmpeg 子进程等待。

## 10. 错误处理与恢复

- 不支持的压缩、加密或损坏文件：终止该词典导入并记录明确错误。
- MDD 缺失或引用不存在：允许导入文本，将缺失项计入统计。
- 无法识别的音频：保留引用诊断，不写入无效资源。
- 分片空间不足或磁盘写入失败：回滚当前分片事务，词典保持非 `READY`。
- FFmpeg 失败：保留任务日志，不覆盖已有目标文件。
- 应用异常退出：启动时检测 `IMPORTING` 状态和孤立临时目录，提供清理或重新导入。

删除词典时，在单个目录库事务中级联删除其词条、例句和音频链接；共享音频资源不会立即删除。随后运行垃圾回收任务，找出已无 `audio_link` 引用的资源，先删除目录记录，再从分片删除 BLOB。分片中的空闲页由计划内维护操作回收，避免每次删除都执行耗时压缩。

## 11. 性能与容量约束

- 精确查词采用索引，热缓存下单词查询目标低于 100 ms。
- 导入采用流式解析和批量事务，进程常驻内存目标低于 1 GB。
- 音频通过 SHA-256 全局去重；目录库不保存音频 BLOB。
- 每个分片约 2 GB，避免单个 10 GB 数据库的备份、校验和恢复成本。
- 导入期间启用 WAL，并在任务结束后 checkpoint；定期提供完整性检查和备份功能。

## 12. 测试策略

- 单元测试：词头规范化、`sound://` 提取、适配器、优先级选择、例句/时长限制和分片轮换。
- 存储测试：迁移、唯一约束、BLOB 去重、崩溃后孤立资源清理和独立线程连接。
- 集成测试：使用最小合成 MDX/MDD 夹具验证导入、查询和资源关联，不提交专有词典。
- 音频测试：生成短测试音频，通过 FFprobe 验证格式、总时长、顺序和静音误差。
- UI 测试：导入取消、优先级拖动、生成进度和错误提示的关键流程。
- 打包测试：在无 Python/Qt 的干净 Windows 虚拟机中安装、启动、导入和生成音频。

## 13. 安全、版权与数据管理

应用不启动网络服务，不上传词典、生词或音频。所有 SQL 使用参数化查询，临时文件名由应用生成。UI 明确提示用户仅导入有权使用的词典，备份功能同时包含 `dictionary.db` 和全部 `audio-NNN.db`，恢复前执行哈希及 SQLite 完整性检查。
